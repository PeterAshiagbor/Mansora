# Browser workspace provisioning (C36)

C36 adds a shop to the running Railway platform through the existing administrator client page. It uses the unchanged retail engine activation contract. No shop restart, default staff, fictional records, owner-password assignment by Mansora or direct retail SQL write is introduced. Client production readiness, trusted proxy throttling/recovery and independent backups remain separately tracked in C37/C38.

## Administrator and owner flow

1. In Clients, create the client with its business name, owner name and correct owner email. Save it, then open the client detail.
2. Select **Browser workspace**. This action is available only when the server has the browser-workspace adapter. It requires the existing authenticated platform administrator session and is rate-limited.
3. Share the private setup link only with that recorded owner through your approved channel. Its proof is in the URL fragment, not a request path. It expires after 30 minutes. Repeating the action while pending returns the same link; an expired pending operation can receive a fresh link. This action does not automatically email anyone.
4. The owner opens the link, chooses and confirms a password of at least 12 characters, and creates the workspace. Password choice is owner-side; the administrator never receives it.
5. The owner is redirected to the workspace login with their email prefilled. They can sign in, add stock/customers and create their own staff using existing permissions. New shops start empty. Billing/subscription approval remains a separate existing workflow.

After successful setup the administrator action returns the ordinary workspace address, without a setup proof. A used proof cannot reset a password or create a second owner. An existing active desktop device is not silently converted into an empty browser store: a new request is refused for operator review. This feature is not a desktop-to-browser migration tool.

## Lifecycle and isolation

The API issues an activation code bound to the selected tenant. The onboarding adapter fixes the API destination to the configured loopback service; a public request cannot select its own API URL, code, tenant or role. It calls the existing `activation.activate`, verifies the resulting tenant identity and authenticates the owner password before publishing the workspace.

Successful registration updates the gateway lookup and the shared workspace list used by sync, scheduled backup and shutdown. Other shops' sessions and stores remain open. Registry metadata binds the dynamic workspace to its tenant and persistent owner email alias. On restart, existing stores and aliases reopen; no new password or default data is applied.

Proof expiry, replay protection, bounded setup requests, one in-flight activation per tenant and at most two concurrent activations are enforced. The existing ten-workspace capacity remains in force. Origin, JSON/body limits, CSP, private cookies, session caps, permissions, encryption, tenant/RLS rules and the managed browser activation restriction remain enabled. The browser cannot invoke unrestricted activation/re-linking through the command gateway.

## Private files and recovery

`/data/staging/browser-onboarding/<tenant>.json` contains tenant/contact metadata, a proof hash, expiry and completion state. Pending proof/code material is encrypted with AES-256-GCM and tenant-bound authenticated data under a separately derived key. The raw owner password is never persisted in this journal. Files are mode 0600 in a mode-0700 directory. Completion clears the encrypted pending secret.

`/data/staging/workspaces.json` includes the dynamic workspace ID, tenant binding and owner email/username alias; store it privately. Retail stores retain their per-workspace derived encryption keys. A restore needs the registry, onboarding journals, retail stores, PostgreSQL and protected master-key material; C38 owns independent storage, retention/key custody and a rehearsed restore. Never publish those files as artifacts.

A crash after activation but before registration can resume with the same valid proof and owner-chosen password. It authenticates the existing owner; it does not rewrite a password hash or recreate an owner. A conflicting tenant/store/registry is preserved and refused for operator review. Do not delete journals or stores to force completion. Expired links, changed pending owner details and failed attempts must not be worked around by weakening identity checks.

## Test-environment behavior

The existing team-test mode/banner and private accounts remain unchanged. The C43 sample-data pack now selects only workspace IDs present in its private test-account manifest, so a new dynamic shop never receives fictional sales, test staff or default credentials. A private CI-only `smoke-third-owner.json` fixture is generated by the explicit acceptance command, not by normal startup.

## Verification and rollout

Integration coverage exercises authenticated administrator requests, owner-side browser setup under CSP, duplicate submissions, wrong/expired/replayed proof, password length checks, retained existing sessions, third-shop isolation, actual background sync, restart persistence, interrupted activation recovery and rejection of a foreign tenant's code. It also checks disabled adapters and bounded administrator requests.

The Railway exact-image acceptance provisions a third synthetic client using the public gateway/API, chooses its owner password through the same completion route, saves a record, recreates containers and requires the same owner login and record. No source or environment toggle bypasses CI gates. The API-only and native desktop builds remain available without this adapter; their client page does not advertise an unavailable action.

Mark C36 deployed only after exact-head CI, merged CI and the Railway terminal SUCCESS/readiness checks pass. Record a live third-shop acceptance separately from local/container evidence; do not infer it from a green build.
